## 0. 本版本定位

v0.1 交付了核心闭环（打开仓库 → 浏览 → 编辑 → 提交 → 推送）。v0.2 不追求与 CodeApp 全面对标（其内置 Python/Node/C++/Java 运行时是 Swift 原生 + WASM 的多年护城河，本项目 React Native/Expo 架构无对等路径），而是**聚焦三个支柱做深**：

1. **Git 工作流深化** — 解决 v0.1 最大痛点（设置不持久），补齐冲突解决、远程分支、PR 创建
2. **编码自动提示与补全** — Java 达到 VS Code 标准（完整 LSP）
3. **AI Coding 体验** — 内联补全 + 对话式 plan-execute，集成 Claude Code / Codex / GLM

差异化逻辑：CodeApp 是"iPad 上的完整本地 IDE"；本项目走"**Git 工作流 + AI 辅助编码的轻量前端**"，把重计算（agent 执行、语言服务器）放到远程，iPad 作为高质量的控制与编辑前端。

## 1. 关键架构决策（需求澄清产物）

以下决策在需求澄清阶段已与产品负责人确认，是 v0.2 全部功能需求的前提。**记录决策本身及其原因，供工程/架构团队据此设计 spec。**

### 决策 A：AI 执行采用「混合架构」

| 能力 | 执行位置 | 原因 |
|---|---|---|
| 内联补全（ghost text） | **设备端** + 模型 API | 内联补全对延迟极度敏感（需 < 数百 ms 出建议），往返远程 agent 不可接受；直连模型 API（FIM/补全端点）延迟最低 |
| 对话式 plan-execute | **远程 Bridge** | Claude Code / Codex 是需要真实执行环境的 agent，iOS 沙盒无法本地运行进程；iPad 作为前端连接远程环境（云开发容器或用户自有机器），形态类似 Claude Code on the web |

**为什么不全设备端：** iOS 沙盒无进程执行能力，无法本地运行 Claude Code/Codex CLI agent（v0.1 spec/modules/04_terminal.md 已确立此约束）。
**为什么不全远程：** 内联补全走远程往返延迟无法满足边打字边提示的体验。

### 决策 B：Java 补全采用「独立远程 LSP 网关」

- Java 达到 VS Code 标准需要 `jdtls`（Eclipse JDT Language Server），它是 JVM 进程，iOS 无法本地运行
- 部署一个**独立的 LSP 网关服务**（可托管或用户自建），iPad 内的 Monaco 通过网络 LSP 协议获取补全
- 与 AI 远程 Bridge **解耦**：LSP 网关只做语言服务，职责单一，可独立演进/扩容
- 代价：多一套基础设施；补全依赖网络（离线降级到 Monaco 内置）

### 决策 C：设置持久化为 v0.2 前置必做

- v0.1 所有设置（Token、作者信息、主题）重启即丢，是预计投诉最多的 UX 问题（v0.1 PRD §8、spec/modules/06_settings.md）
- v0.2 新增的 AI Key、Bridge 端点、LSP 网关地址同样需要持久化，否则三大支柱都无法实用
- 因此设置持久化是 v0.2 的**地基**，列为 P0 之首

## 2. 问题陈述

### v0.1 遗留痛点

1. **设置不持久** — 每次启动重输 Token、作者信息、重开工作区（v0.1 已知缺口）
2. **无智能补全** — 仅 Monaco 内置，无跨文件跳转、无类型分析、无诊断（v0.1 无 LSP）
3. **Git 工作流不完整** — 无冲突解决引导、无远程分支可见性、无法在应用内创建 PR
4. **无 AI 辅助** — 飞机/咖啡馆场景下，开发者需要 AI 帮助理解陌生代码、生成与重构，v0.1 完全缺失

### v0.2 要解决的核心问题

> "我在 iPad 上想要的不只是能改代码并推送，而是像在 MacBook 上用 VS Code + Copilot + Claude Code 一样：有靠谱的补全，能让 AI 读懂我的仓库、规划并执行修改，且我的配置不会每次丢失。"

---

## 3. 目标用户（沿用 v0.1，强化 AI 场景）

主要画像不变（资深移动开发者、计算机专业学生）。v0.2 强化两类场景：

- **Java 开发者**：在 iPad 上审阅/修改 Java 项目，需要 IDE 级补全（明确的 LSP 目标语言）
- **AI 优先的开发者**：习惯 Claude Code / Codex 工作流，希望在 iPad 上延续 plan-execute 的协作方式

### v0.2 新增前提

- 对话式 AI 与 Java 补全**需要网络**及对应的远程后端（Bridge / LSP 网关）。纯离线用户仅能使用 v0.1 能力 + 设备端内联补全（取决于所选模型是否支持离线，v0.2 默认内联补全也走云 API）。

## 4. 产品目标（v0.2）

| 目标 | 指标 | 目标值 |
|---|---|---|
| 设置持久化 | 重启后 Token/作者/工作区/AI 配置保留 | 100% 保留，Token 入 Keychain |
| Java 补全达标 | 自动补全 + 跨文件跳转 + 诊断 + 悬浮 | 与 VS Code 行为一致 |
| 内联补全可用 | ghost text 出现到可接受 | P50 < 800ms（依赖网络/模型） |
| 对话式 plan-execute | 规划→展示 diff→确认→执行闭环 | 端到端在应用内完成 |
| 多 AI Provider | Claude / Codex / GLM 可切换 | 至少 3 家可配置并正常工作 |
| 冲突可解决 | pull 冲突后应用内解决并提交 | 无需借助桌面端 |

## 5. 功能需求

### 支柱一：Git 工作流深化

#### P0

**F01：设置持久化（地基）**
- **内容：** Token 与 AI/Bridge 密钥存入 `expo-secure-store`（iOS Keychain）；作者信息、主题、字体、Bridge 端点、LSP 网关地址等偏好存入 `settings.json`
- **原因：** v0.1 最大痛点；v0.2 新能力（AI Key、Bridge、LSP）均依赖持久化
- **验收标准：** 杀掉应用重启后，无需重新输入任何凭证或配置即可继续推送、补全、对话
- **约束：** 任何密钥（GitHub Token、AI API Key、Bridge 凭证）**仅入 Keychain，禁止写入 `settings.json` 或日志**

**F02：工作区持久化与「最近工作区」**
- **内容：** 记录已打开工作区列表；启动时可一键重开上次工作区
- **原因：** v0.1 US03 已标注的已知缺口（会话间不持久）
- **验收标准：** 重启后首屏显示最近工作区列表，点击直接进入

#### P1

**F03：合并冲突解决 UI**
- **内容：** `pull` 产生冲突时，列出冲突文件；提供冲突标记（`<<<<<<<` / `=======` / `>>>>>>>`）的可视化解决界面（采用本地/远程/手动编辑）；解决后暂存并提交
- **原因：** v0.1 仅显示错误信息，无引导（spec/modules/03_git.md 已知限制 §3）
- **验收标准：** 构造一个冲突 pull，能在应用内完成解决 → 暂存 → 提交，无需外部工具

**F04：远程分支可见性**
- **内容：** 分支列表中展示远程分支（`origin/*`），支持基于远程分支检出本地跟踪分支
- **原因：** v0.1 仅列本地分支（spec/modules/03_git.md §分支操作 已标注待办）
- **验收标准：** 克隆仓库后能看到并检出远程分支

**F05：GitHub PR 创建**
- **内容：** 复用现有 `github.ts`（Octokit），从当前分支向目标分支创建 PR，填写标题/描述
- **原因：** 主用户画像核心场景"在 iPad 上审查 PR"，闭环需要能发起 PR
- **验收标准：** 推送分支后，应用内创建 PR 并返回 PR 链接

---

### 支柱二：编码自动提示与补全（LSP）

#### P0

**F06：Monaco LSP 客户端集成**
- **内容：** 在 Monaco WebView 中接入 LSP 客户端，通过网络与远程 LSP 网关通信（语言服务器在网关侧运行）
- **原因：** Monaco 原生不带语言服务器；jdtls 无法在 iOS 本地运行（决策 B）
- **验收标准：** 编辑器能向网关发起 LSP 请求并渲染返回的补全/诊断/悬浮

**F07：LSP 网关连接配置**
- **内容：** 设置中配置 LSP 网关地址与凭证；显示连接状态；连接失败时降级到 Monaco 内置补全并提示
- **验收标准：** 配置有效网关后状态显示「已连接」；断网时编辑器仍可用（降级）

**F08：Java 完整补全（VS Code 标准）**
- **内容：** 通过网关的 jdtls 提供：自动补全（含导入建议）、悬浮文档、**跨文件跳转定义/引用**、诊断（错误/警告波浪线）、签名提示、重命名符号
- **原因：** 产品负责人明确要求 Java 达到 VS Code 标准
- **验收标准：** 打开真实 Java 项目，上述每项行为与桌面 VS Code 一致

#### P1

**F09：LSP 多语言扩展（TypeScript / Python）**
- **内容：** 同一网关机制扩展到 TS（tsserver）、Python（pyright）
- **原因：** 复用 F06/F07 架构，边际成本低；TS/Python 是目标用户高频语言
- **验收标准：** TS/Python 文件具备补全 + 跳转 + 诊断
- **备注：** 优先级低于 Java；Java 必须先达标

---

### 支柱三：AI Coding 体验

#### P0

**F10：AI Provider 配置（多家）**
- **内容：** 配置并切换 Claude、OpenAI/Codex、GLM；分别设置内联补全所用模型 API Key，以及对话式所用 Bridge 端点
- **原因：** 决策 A 混合架构，内联与对话走不同通道；用户自带 Key
- **验收标准：** 三家均可配置；切换后内联与对话分别使用对应 Provider；密钥入 Keychain
- **约束：** Provider 密钥**禁止出现在日志、错误信息、崩溃报告**（沿用并扩展 v0.1 Token 不变量）

**F11：内联补全（ghost text）**
- **内容：** 编辑时以灰字展示 AI 建议；Tab 接受、Esc 拒绝、可逐词接受；走设备端模型 API（直连，非 Bridge）
- **原因：** 决策 A——延迟敏感，必须直连
- **验收标准：** 输入时出现合理补全，Tab 写入编辑器；不阻塞打字（异步、可取消）
- **约束：** 补全请求必须可被新输入打断（abort 机制），避免过期建议覆盖

**F12：对话式 AI 面板（plan-execute）**
- **内容：** 侧边栏聊天面板，连接远程 Bridge 上的真实 agent（Claude Code / Codex / GLM）；支持两段式：**先 Plan（展示拟修改文件与思路）→ 用户确认 → 再 Execute（落盘）**
- **原因：** 决策 A——真实 agent 文件操作能力需远程执行环境；plan-execute 是产品负责人指定的交互范式
- **验收标准：** 提问"重构这个函数"→ 返回计划与 diff 预览 → 用户批准 → 变更写入工作区文件
- **关键安全约束：** **执行（落盘）前必须展示 diff 并经用户显式确认，禁止静默写盘**

**F13：AI 变更审阅与应用**
- **内容：** AI 产生的修改以 diff 形式呈现（复用 v0.1 GitDiffView / Monaco diff），可逐文件接受/拒绝；接受后写入工作区
- **原因：** plan-execute 的可信前提是变更可见、可控
- **验收标准：** 多文件变更能逐一审阅；接受后文件树与 Git 状态正确刷新

#### P1

**F14：Bridge 连接管理**
- **内容：** 连接/断开远程 Bridge 环境；显示连接状态、当前会话；断线重连
- **验收标准：** Bridge 不可用时对话面板给出清晰提示，不影响编辑器与 Git 本地功能

**F15：AI 上下文注入**
- **内容：** 对话时自动附带当前文件/选区/工作区结构作为上下文；可手动 @ 引用文件
- **验收标准：** AI 回答能感知当前打开的文件内容

## 6. 用户故事

### US01 — 配置一次，长期使用
> 作为资深开发者，我希望配置一次 Token、AI Key、作者信息后，重启应用仍然保留，不必每次重输。

**验收：** 重启后直接可推送、可补全、可对话。

### US02 — Java 项目的 IDE 级体验
> 作为 Java 开发者，我在 iPad 上打开 Spring 项目，希望自动补全方法、跳到定义、看到编译错误，就像桌面 VS Code。

**操作流程：** 配置 LSP 网关 → 打开 `.java` 文件 → 输入触发补全 → ⌘点击跳转定义 → 错误处显示波浪线。

### US03 — AI 内联补全顺手写代码
> 作为开发者，我边写边获得灰字建议，Tab 一下就接受，不用停下来思考样板代码。

**验收：** 建议及时出现且不卡输入。

### US04 — 让 AI 规划并执行重构
> 作为开发者，我选中一段代码让 AI"提取成独立函数并更新所有调用点"，希望先看到它的计划和 diff，确认后再落盘。

**操作流程：** 选区 → 对话面板提问 → 查看 Plan + diff 预览 → 批准 → 变更写入 → Git 面板出现改动 → 暂存提交推送。
**验收：** 全程在应用内；执行前必有确认步骤。

### US05 — 在 iPad 上完成冲突 pull
> 作为开发者，pull 时遇到冲突，希望在应用内看到冲突、选择保留哪边并提交，而不是被一句错误信息卡住。

**验收：** 应用内完成冲突解决 → 提交。

## 7. 非功能性需求

### 性能
| 场景 | 目标值 | 备注 |
|---|---|---|
| 内联补全出建议 | P50 < 800ms | 依赖网络与模型；超时则静默放弃 |
| LSP 补全响应 | P50 < 500ms | 网关侧已 warm 的前提下 |
| LSP 首次连接（冷启 jdtls） | < 15s | jdtls 索引项目耗时，需有加载态 |
| 设置读取（启动） | < 100ms | Keychain + settings.json |
| 对话式首 token | < 3s | 依赖 Bridge 与模型 |

### 可靠性
- 远程依赖（Bridge / LSP 网关 / AI API）不可用时，**本地能力（编辑、本地 Git、文件树）必须不受影响**，并给出清晰降级提示
- AI 落盘必须经 diff 确认；任何写盘走统一文件系统，写后刷新 Git 状态与文件树
- 应用切后台再回前台，Bridge/LSP 连接应能自动重连或明确提示重连

### 安全性（在 v0.1 基础上扩展）
- 密钥范围扩大：GitHub Token、AI API Key（×3 家）、Bridge 凭证、LSP 网关凭证——**全部仅入 Keychain，禁止写入磁盘明文 / 日志 / 错误信息 / 崩溃报告**
- 内联补全会把代码片段发送到第三方模型 API；对话会把上下文发送到 Bridge——**必须在设置中明示数据外发，并提供开关**
- Bridge 与 LSP 网关连接强制 TLS；用户自建端点需校验证书
- AI 执行的文件变更不得绕过 diff 确认（防止 prompt 注入导致的意外写盘/数据外泄）

### 兼容性
- 沿用 v0.1：iPadOS 17+、Expo SDK 51、Monaco 0.45（固定）
- LSP 网关与 Bridge 的协议/部署形态由架构团队在 spec 中定义（本 PRD 不约束实现）

## 8. 核心不变量（v0.2 新增/强化）

> 供 AI 助手与工程团队遵守，避免延续 bug 或破坏架构。

1. **统一文件系统延续：** AI 与 LSP 引发的一切文件写入仍通过 `expo-file-system`，确保 Git 完整感知（继承 v0.1 不变量 §1）。
2. **密钥仅入 Keychain：** 所有凭证（Token / AI Key / Bridge / LSP 凭证）只存 `expo-secure-store`，绝不入 `settings.json`、日志、错误信息、崩溃报告。
3. **AI 落盘必经确认：** plan-execute 的执行阶段在写盘前必须展示 diff 并获得用户显式确认；禁止静默写盘。
4. **远程不可用不阻塞本地：** Bridge / LSP / AI API 任一不可用时，编辑、本地 Git、文件树、搜索必须照常工作（仅对应增强能力降级）。
5. **写盘后刷新一致性：** 任何 AI/LSP/Git 写操作后，必须刷新 Git 状态、文件树与受影响标签内容（继承并扩展 v0.1 不变量 §3）。
6. **补全可中断：** 内联补全请求必须可被后续输入取消，过期结果不得覆盖编辑器（继承 v0.1 搜索的 abort 模式精神）。
7. **数据外发透明：** 任何把用户代码发送到第三方（模型 API / Bridge）的行为必须可被用户感知并可关闭。

## 9. v0.2 范围外

| 功能 | 原因 |
|---|---|
| 本地语言运行时（Python/Node/C++/Java 执行） | CodeApp 式护城河，RN 架构无对等路径；不在本项目战略方向 |

| 离线 Monaco | 继承 v0.1，仍为 v0.3 目标 |
| App Store 上架 | v1.0 |

## 10. 风险与缓解

| 风险 | 可能性 | 影响 | 缓解措施 |
|---|---|---|---|
| 内联补全网络延迟差 | 高 | 高 | 超时静默放弃；可调触发延迟；探索就近模型/缓存 |
| Bridge 远程环境不可用 | 中 | 高 | 明确降级提示；本地能力不受影响；断线重连 |
| LSP 网关运维成本/可用性 | 中 | 中 | 解耦部署；支持托管与自建；冷启动加载态 |
| 多 Provider API 差异大 | 高 | 中 | 抽象统一 Provider 接口；逐家适配并测试 |
| 密钥泄露面扩大（多 Key + Bridge） | 中 | 高 | 全量 Keychain；发布前安全清单逐项核查 |
| 代码外发引发合规/隐私担忧 | 中 | 高 | 明示数据外发 + 开关；文档说明各通道去向 |
| prompt 注入致 AI 误操作/外泄 | 中 | 高 | 落盘必经 diff 确认；限制 agent 可触达范围 |

## 12. 与 CodeApp 的定位差异（决策背景）

基于功能对比（见会话分析），v0.2 有意**不**正面对标 CodeApp 的本地运行时：

- CodeApp：Swift 原生 + 内置 Python/Node/C++/PHP/Java 运行时 + WASM，定位"iPad 完整本地 IDE"
- 本项目 v0.2：React Native 跨平台前端 + 远程算力（Bridge/LSP），定位"**Git 工作流 + AI 辅助编码前端**"

差异化优势：跨平台潜力、AI-first 工作流（plan-execute 原生集成）、文档/不变量显性化带来的可演进性。短板（无本地运行时）通过"远程执行 + AI 辅助"的产品定位主动规避，而非补齐。
